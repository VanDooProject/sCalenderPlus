# M2 Review — October 2026

Scope: milestone M2 (issues #40–#52: calendars, grants, group lifecycle, events, window query, permission overrides, access explainer, move, share revocation, recurrence and occurrence edits) at commit `fb80a0d`, i.e. `git diff 3b83f33..fb80a0d`, focusing on the layers built on top of the pure permission engine (already reviewed adversarially in [the engine review](2026-10-permission-engine-review.md)). Reviewer stance: security first (what can someone with engine level `none` or `free_busy` learn, what can a lower level change), then authorization correctness under concurrency, recurrence correctness, the sync log / `acl_version` consistency that the iCal feeds of M4 will rely on, and maintainability/performance. Severity: **high** = data exposure without preconditions; **med** = exposure, escalation, data corruption or DoS with preconditions, or a privacy-relevant product rule broken; **low** = robustness, performance, defence in depth; **info** = by design or accepted, documented.

Method: read every M2 endpoint, contract and use case against [api.md](../architecture/api.md), [permissions.md](../architecture/permissions.md), [data-model.md](../architecture/data-model.md) and [plans.md](../product/plans.md); followed each response shape for the busy projection (single `GET`, window with and without `expand=occurrences`, embedded `exceptions[]`, create/update/split/move/occurrence responses, problem `extensions`, ETags); listed every mutation path and checked its `calendar_changes` rows and `acl_version` bumps (§4); reproduced each finding with an integration test (Testcontainers PostgreSQL) or a Core unit test before fixing it.

## 1. Findings

| # | Sev | Area | Finding | Resolution |
|---|---|---|---|---|
| F1 | med | `Api/Events/EventContracts.cs` (#50) — busy projection | The busy projection of a series master listed **every** exception: a moved **transparent** occurrence showed where it moved to (transparent events are otherwise hidden from `free_busy` viewers, §2.1), and exceptions that only changed title/description/location told the viewer "this occurrence was edited". | **Fixed** (`9f3b510`): busy viewers get only cancelled, moved or transparency-changing exceptions; transparent ones without their times. Test `Busy_projection_of_a_master_lists_only_exceptions_that_change_busy_time`. |
| F2 | med | Frozen calendars (#42, #44, #48) | plans.md: frozen calendars refuse create/edit/move-in but allow **deletes and taking access away** ("so owners can clean up", "downgrades never leak"). The api refused event deletes, moves out and **every** grant change — an owner on a downgraded plan could not revoke someone's access without upgrading. | **Fixed** (`6134a0e`): event delete, move-out, grant lowering and removal are allowed; new/raised grants, edits and move-in stay `409 calendar_frozen`. Tests updated/added (`Frozen_calendars_refuse_new_and_raised_grants_but_allow_taking_access_away`, `…_refuse_moves_in_but_not_out`, `…_which_still_allows_deletes`). |
| F3 | med | `EventOccurrenceService.SplitAsync` (#51) — recurrence | The new series of a split starts at the chosen occurrence, whose start anchors the rule (default weekday, day of month, time of day). Splitting at an **RDATE** (e.g. Wed 9:00 of a Mon 18:00 series) turned the rest into a Wednesday-9:00 series; splitting at an occurrence **shifted by a DST gap** (2:30 → 3:30) moved every later occurrence to 3:30 and silently dropped their exceptions (keys at 2:30 no longer matched). | **Fixed** (`a26b101`): such occurrences answer `400` like the first one (`RecurrenceSet.IsRuleOccurrence`, nominal wall clock check). Test `Splitting_needs_an_occurrence_of_the_rule_at_its_nominal_time` (also asserts the next day still splits at 2:30 with the right `COUNT`). |
| F4 | med | Window query (#45, #50) — DoS | Each expansion stops after 1,000,000 examined days, but one window query expands up to 5,000 series and `COUNT` rules cannot jump to the window: 5,000 rarely matching `COUNT` series queried far from their start cost billions of steps per request (any user can create them in their own calendar and query them). | **Fixed** (`7374808`): all expansions of a window share an `ExpansionBudget` of 5,000,000 examined days; beyond it the response is `truncated`. Core test `A_shared_expansion_budget_bounds_the_days_all_expansions_of_a_request_examine`. |
| F5 | med | `acl_version` for M4 feed caches (#41, #43) | Creating a calendar bumped nothing (a new group calendar appears in every member's aggregate feed); deleting one bumped only its grantees — not the owner (user or group) and not the users/groups its events' **overrides** named, whose "Shared with me" loses those events; changing role defaults bumped only the calendar, not the owning group whose members' levels changed (grant changes do bump the group they name). A feed cache keyed on `acl_version` would serve deleted events. | **Fixed** (`6e36f6d`): create bumps the owner, delete bumps owner + grantees + override principals (`EventQueryService.OverridePrincipalsAsync`), role-default changes bump the owning group. Test `Creating_and_deleting_a_calendar_bump_its_owner_and_the_people_its_events_name`. |
| F6 | low | Share revocation (#49) | Lowering role defaults takes calendar level away from members exactly like lowering a grant, but did not revoke their individual event shares (§4.6 asymmetry: an `edit` share stayed an elevation above the new level). | **Fixed** (`6e36f6d`): `EventShareRevocation.OnRoleDefaultsChangedAsync`, opt-out `PATCH /calendars/{id}?revokeEventShares=false`; the calendar update now runs in one transaction. Test `Lowering_role_defaults_revokes_the_shares_of_members_who_lose_level`. permissions.md §4.6 updated. |
| F7 | low | `occurs_range` (#50) | Series ranges ended at `series_until_utc` exclusively. A series without duration (start = end) ends where its last occurrence starts, so a window starting there (a day view at midnight) never saw it, and a `COUNT=1` zero-length series had an empty range and was never listed. The "Shared with me" query had the same `>`. | **Fixed** (`4201170`, `b1e6420`): series ranges are inclusive (migration `InclusiveSeriesOccursRange`, column and GiST index re-created), `>=` in the shared query. Test `Zero_length_series_are_found_at_their_last_occurrence`. |
| F8 | low | Window query (#45) — performance | "Shared with me" loaded the ids of **every** event ever shared with the caller (all time) and then those events by id, on every window request — unbounded `IN` lists for long-lived accounts and members of groups with many group shares. | **Fixed** (`b1e6420`): one query with the window's bounds and an `EXISTS` over `event_overrides(principal_type, principal_id)`, at most 5,000 rows (`truncated` beyond); `IEventOverrideSource.EventsNamingAsync` removed. Existing window/shared tests cover the behaviour. |
| F9 | low | Revocation / group deletion — performance | Revocations loaded (tracked) every event sharing with the affected users in **any** calendar, and both revocations and group deletion ran one `UPDATE` and one subject query **per calendar**. | **Fixed** (`b1e6420`): events only of the calendars where level was lost (`ForLifecycleAsync(…, calendarIds)`), `AclVersions.BumpCalendarsAsync` and `CalendarAudit.BillingSubjectsAsync` in one statement each. |
| F10 | low | TOCTOU — event writes vs. ACL changes | Event create/update/delete and occurrence edits check the level outside any lock shared with ACL changes; `xmin` guards the event row only. A grant removal or membership change racing a write lets that one write commit just after the actor lost access, and an override replacement racing a grant removal can leave a share the revocation would have removed (write skew: each transaction read the other's pre-state). | **Not fixed** (documented): needs a protocol, not a patch — e.g. ACL-dependent writes take `SELECT … FOR SHARE` on the calendar row before reading grants, and ACL changes update the calendar row (`acl_version`) *before* reading dependent state; memberships need the same via the user row. The window is milliseconds and the outcome equals the write arriving slightly earlier; split, move and override replacement already re-check inside their transaction. Recommended before M4 share links. |
| F11 | info | `uid_conflict` | A contributor creating an event with a chosen `uid` learns from `409 uid_conflict` that the calendar holds a (possibly hidden) event with that UID; same for moves. | **Accepted**: UIDs are unique per calendar (RFC 5545, CalDAV); the caller must already know the UID; native UIDs are random UUIDv7. |
| F12 | info | Transparent masters | A transparent series master with opaque exceptions is hidden from `free_busy` viewers entirely (window without `expand`, `GET`), and its opaque occurrences too in master mode. | **Accepted**: under-sharing, not a leak; `expand=occurrences` shows the opaque occurrences. Noted for the UI. |
| F13 | info | Split vs. plan limits | Split copies overrides without a plan check (documented, permissions.md §4.6), so repeated splits can push `events_with_overrides` above the limit; afterwards only removals pass for that plan subject. | **Accepted** (spec decision, no new privacy decision); revisit with billing. |
| F14 | info | Explainer, own level | A `free_busy` viewer explaining their own level sees `override_matched` steps (e.g. `everyone → free_busy`), i.e. that the event has overrides, which the busy projection omits (`hasOverrides`). | **Accepted**: it is their own access and its reason (the purpose of the endpoint); no principals beyond what matched them. |
| F15 | low | Maintainability | `SaveAsync` with the `DbUpdateConcurrencyException → 412` mapping is duplicated in five services; time parsing/validation (`EventService.ParseTimes`, `StartInput`/`EndInput`) is reused by the occurrence service through `internal static` members of another service. | **Not fixed**: small and consistent; extract a shared `SaveOrPreconditionFailedAsync` and an `EventTimesInput` parser when M3/M4 add callers. |

Checked and found sound: every calendar/event endpoint answers `404` for level `none` before any other check (incl. occurrence routes: the series level is checked before the occurrence is looked up, so a `free_busy` viewer gets `403`, never an occurrence oracle); `calendarIds` with invisible ids are ignored (shared events from them only when the caller is named); busy projection on single `GET`, window items (no `etag`), occurrences (`occurrenceId`, `recurrenceId`, `recurrence` only), and ETags hash only the representation the caller sees; create/update/split/move responses and `droppedExceptions`/`relatedTo`/`uid` only reach callers at `edit`+; problem `extensions` (`required`/`actual`, `violations`) carry only the caller's own levels and the principals they proposed or (move: `manage` on the event) may see; override list only for floor holders (`manage`); grant list only for managers; explaining another user needs calendar `manage` and a user the caller can see (unknown ids `404`); "Shared with me" items carry an opaque `calendarId` that answers `404`; cursors are the last item's UUID — tampering only moves the start, items are still resolved by the engine; audit rows are not readable through the api (event snapshots contain details — filter by level when an audit UI comes); `If-Match` required on every promised change (calendar/grant/event/occurrence/split/move/overrides); plan limits counted under advisory locks on the plan subject; move/split keep the creator and re-validate/copy overrides as specified; group deletion removes grants and group overrides in the group's transaction; no event or exception row is written outside `EventWriter`/`EventQueryService`-loaded tracked entities (architecture test plus the review of every `db.Event*` use); DST: occurrences keep the first occurrence's wall clock, gaps shift forward with the nominal recurrence id, all-day series are floating dates; caps (`COUNT` ≤ 5,000, `INTERVAL` ≤ 1,000, ≤ 100 RDATEs, ≤ 1,000 EXDATEs, rule ≤ 500 characters, 13-month windows, 200 `calendarIds`, 200 override entries).

What every M2 mutation writes for sync clients (`calendar_changes`) and caches (`acl_version`) after this review. "Principals" = the users/groups named by the changed grants or overrides (`anonymous`/`everyone` have no version). Bold entries were added by this review.

| Mutation | `calendar_changes` | `calendars.acl_version` | `users`/`groups.acl_version` |
|---|---|---|---|
| Calendar create | — (no events) | new row | **owner (user or group)** |
| Calendar update: name, description, color, zone | — | — (feeds must also key on `updated_at`, see §3) | — |
| Calendar update: `creators*` settings | — | +1 | — |
| Calendar update: role defaults | — | +1 | **owning group**; lowering: revocation rows below |
| Calendar delete | rows cascade with the calendar | row deleted | grantees, **owner, override principals of its events** |
| Grant create / update / delete | — (see §3, sync tokens) | +1 | the grantee (user or group); lowering/removal: revocation rows below |

| Event update / series "all" | `upsert` | — | — |

## 3. Recommendations

### M3 (UI)

- Busy projection: render an exception with `transparency: transparent` and no times as "free" (nothing); never infer details from missing members.
- Offer "this and following" only on occurrences of the rule (not on `rdates`, not when the occurrence was shifted by a DST gap — the api answers `400`); "this occurrence" works everywhere.
- Frozen calendars: keep delete, move-out, lowering/removing grants and removing overrides enabled; show why the rest is disabled.
- Role-default editing and grant lowering/removal: show the "also revoke their individual event shares" checkbox (`revokeEventShares`).
- Handle `truncated: true` (offer a smaller window), and use list `etag`s / series ETags as `If-Match` without an extra `GET`.

### M4 (iCal feeds, sync)

- Cache keys: per calendar `calendars.acl_version` + `max(calendar_changes.seq)` + `calendars.updated_at` (name/colour/zone changes bump no version); aggregate feeds `users.acl_version` + the `groups.acl_version` of the user's groups + the visible calendars' keys; "Shared with me" additionally `max(seq)` over the calendars of the shared events — content changes of a shared event bump nobody's `acl_version`.
- Sync tokens (`/changes`, CalDAV `sync-collection`): a change of `calendars.acl_version` must invalidate incremental tokens (a grant change alters every event's projection without change rows).
- Reuse the api's projection rules (busy exceptions per F1, transparent events omitted below `read`) and the `ExpansionBudget` in feed generation; use Ical.Net only for serialization.
- Before share links (anonymous principals), implement the calendar-row fence of F10 so link creation/revocation and event writes serialize.
