# M1 Review — October 2026

Scope: milestone M1 (issues #25–#36: problem details, authorization matrix, job queue and email, audit, Identity cookie sessions, CSRF, rate limiting, TOTP 2FA, profile, groups, membership, invites) at commit `e159cee`, i.e. `git diff ebd45b7..e159cee -- backend frontend e2e deploy` plus the resulting code. Reviewer stance: security first (authentication, authorization, data handling), then correctness under concurrency, test quality and maintainability. Severity: **high** = account takeover or secret leak; **med** = exploitable weakness with preconditions (stolen session, timing); **low** = robustness, defence in depth, contract quality.

Method: read every M1 endpoint and use case against [api.md](../architecture/api.md), [permissions.md](../architecture/permissions.md) §6 and [data-model.md](../architecture/data-model.md); traced each request through forwarded headers → authentication → rate limiter → CSRF → authorization → use case → transaction; reproduced concurrency findings with parallel requests against PostgreSQL (Testcontainers); ran the `web` Caddyfile in `caddy:2-alpine` and inspected its logs for the email-link URLs.

## 1. Findings

| # | Sev | Area | Finding | Resolution |
|---|---|---|---|---|
| F1 | high | `deploy/caddy/web.Caddyfile` | The email links (`/verify-email?…&token=`, `/reset-password?…&token=`, `/invite?token=`) are SPA routes served by `web`. Caddy's access log recorded the full URI, and the SPA's API calls from such a page send it again as same-origin `Referer` (also logged, in the error log too). Password-reset tokens in the log pipeline = account takeover for 24 h; invite tokens = group access. | **Fixed** (`e4714eb`): `multi_regexp` masks the value of every query parameter whose name contains `token` in `request>uri` and `Referer`, next to the `/ical/` masking. Verified in the container: URI, Referer and the 502 error log show `token=[REDACTED]`; coolify.md updated. |
| F2 | med | `Auth/TwoFactorEndpoints.cs` (#31) | Enabling 2FA needed only the session. A stolen session (or XSS) could put the account behind the attacker's authenticator; a password reset does not remove 2FA, so the owner was locked out permanently. Also possible on unverified accounts: whoever registered a stranger's address could enable 2FA before the owner reclaimed it via password reset. | **Fixed** (`a7d4225`): `POST /me/two-factor/enable { code, password }` (wrong password → `403 reauthentication_failed`), setup and enable require a verified email, enable is rate limited per IP. Tests + matrix cases. |
| F3 | med | `Auth/TwoFactorEndpoints.cs` (#31) | The password/code confirmation of disable and regenerate (`CheckPasswordAsync`, `VerifyTwoFactorTokenAsync`) ignored the lockout and counted no failures: with a stolen session the password could be guessed at 10/min per IP from as many IPs as available. | **Fixed** (`a7d4225`): confirmations refuse locked-out accounts, count failures towards the lockout (5 → 15 min, `user.locked_out` audited) and reset the count on success. |
| F4 | med | `Auth/AuthEndpoints.cs` (#28) | Account enumeration by timing: Identity refuses a locked-out account *before* verifying the password, so its failed login skipped the ~100 ms hash that unknown addresses pay (dummy hash). Five wrong guesses plus one timed request revealed whether an address is registered. | **Fixed** (`3ec010b`): locked-out logins hash against the dummy too; test with a counting password hasher (locked and unknown: exactly one hash each). |
| F5 | med | `Groups/GroupMembershipService.cs` (#35) | The `xmin` serialization of membership changes only worked when `updated_at` actually changed. With an equal clock reading EF skipped the group UPDATE and its version check: a billing transfer to an owner and that owner leaving at the same time both succeeded, leaving a **non-member as billing owner** (reproduced deterministically with the tests' fixed clock; in production only with equal timestamps, but the invariant must not depend on the clock). | **Fixed** (`bfc96d1`): the group column is marked modified explicitly (`Touch`), so every membership change writes the row. Regression test runs the race five times and asserts the billing owner is always a member with role owner. |
| F6 | low | `Groups/GroupInviteService.cs` (#36) | Frozen groups refused *new invites* but still admitted members through invites created before the freeze (links up to 1000 uses, auto-join on email confirmation). | **Fixed** (`2f7f1db`): accept → `409 group_frozen`; auto-join leaves the invite pending; confirming the address still succeeds. |
| F7 | low | `Groups/GroupInviteService.cs` (#36) | Joining saved the tracked group with its `xmin` check, so people accepting a shared link at the same moment got `412 precondition_failed` on a POST without a precondition. | **Fixed** (`2f7f1db`): the group row is touched with an unconditional `UPDATE` (still serializes against role changes; joiners of one invite are serialized by the invite row lock). Tests: 5 parallel joins all succeed; 4 parallel accepts of a link's last use → exactly one joins. |
| F8 | low | OpenAPI / `api-client` (#25) | Known open item: integers were `integer \| string` in `v1.json` and `number \| string` in `schema.d.ts` (incl. `limit`, `memberCount`, `uses`, problem `status`). Cause: the minimal API web JSON defaults (`JsonNumberHandling.AllowReadingFromString`) feed the schema generator. | **Fixed** (`096e320`): strict number handling (`ConfigureHttpJsonOptions`); numbers sent as strings are `400`. Test rejects mixed integer/string schemas in the committed document. The PR-time `oasdiff` check may flag narrowed request types against a base that already has M1 (label `api-breaking-approved`; no client sends strings). |
| F9 | low | Authorization matrix (#26) | Cases asserted the status code only, so a `403 csrf_header_missing`/`email_not_verified` or a `404` from a mistyped route passed for a permission decision. | **Fixed** (`2fc06fe`): error cases assert the problem `code` too (status default: 401 `unauthenticated`, 403 `insufficient_permission`, 404 `not_found`, 409 `conflict`; explicit otherwise). |
| F10 | low | Tests | Missing negative/concurrency tests: other sessions after a password reset, concurrent redemption of one recovery code, max-uses race, membership race. | **Added** (`a7d4225`, `3ec010b`, `bfc96d1`, `2f7f1db`). The recovery-code race is safe (Identity's concurrency stamp on the user row; the loser fails), now pinned by a test. |
| F11 | low | `GroupInviteService` | `GetViewAsync` duplicated `GroupService.GetAsync`. | **Fixed** (`2f7f1db`). |
| F12 | low | `forgot-password` | Known addresses write an outbox job and an audit row, unknown ones nothing: a few ms of timing difference. | **Not fixed**: rate limited (10/min per IP), much smaller than the hash difference of F4; equalizing would mean fake writes. Revisit if the endpoint is ever unlimited. |
| F13 | low | Identity TOTP | A TOTP code can be reused within its ±2-step window (Identity has no replay cache). | **Not fixed**: needs a per-user last-used-step column; low value while login is also password-gated and rate limited. Candidate for the sessions work (v1). |
| F14 | low | Logout | `POST /auth/logout` clears the cookie but does not revoke the ticket server-side; a copied cookie stays valid until it expires (14 days sliding) or the security stamp changes. | **Not fixed** (planned): server-side session list/revoke is the v1 `sessions` endpoint (api.md §3). |
| F15 | low | Pre-registration | Someone can register a stranger's address; if the owner clicks the confirmation email anyway, the account is verified with the registrant's password (and auto-joins pending invites). | **Accepted**: the email says to ignore it; F2 removes the 2FA lock-in; a password reset by the owner ends the other sessions (tested). |
| F16 | low | Job queue | Dead-lettered `email.send` jobs keep the rendered email (with its link token) in `jobs.payload`. | **Not fixed**: tokens expire (1 day; invites ≤ 30 days and revocable); dead letters are needed for diagnosis. Consider scrubbing payloads of dead-lettered email jobs with a retention job (M4 operations). |
| F17 | low | Invites | Pending invites survive the demotion/removal of their creator; a removed member can rejoin with a link that still has uses. | **Accepted** (design): admins/owners see and revoke pending invites; documented behaviour of links. |
| F18 | low | Forwarded headers | `ReverseProxy__KnownNetworks` defaults to all private ranges; on Coolify's shared `coolify` network another stack's container could reach the api directly and spoof `X-Forwarded-For` (rate-limit partition, audit IP). | **Not fixed**: requires a compromised neighbour container; operators can narrow `TRUSTED_PROXY_NETWORKS` to the stack's network (documented in `.env.example`). |
| F19 | low | Caddy | The token masking matches literal parameter names; a percent-encoded name (`%74oken=`) is not masked. | **Accepted**: the backend only generates literal `token=` links; a crafted encoding only exposes the crafter's own token. |

Checked and found sound: secure-by-default `/api/v1` group (every anonymous endpoint opts out and is listed with a reason), the pending-2FA cookie never authenticates protected endpoints (matrix), cookie flags (`__Host-`, `Secure`, `HttpOnly`, `SameSite=Lax`, no `Domain`) for session and 2FA cookies, CSRF on every unsafe `/api` request incl. anonymous ones (bearer exemption only without the session cookie; `Authorization` is not CORS-safelisted), CORS closed, rate-limit partitions after trusted forwarded headers only (`ForwardLimit` unbounded but stops at the first untrusted hop), reset tokens single-use via the security stamp, reset/2FA changes rotate the stamp, recovery codes stored as SHA-256 and compared in constant time, invite tokens 256-bit random and stored hashed (never in responses after creation, never in audit), email invites bound to the verified address, link role ≤ member, admins assign ≤ member and cannot act on admins/owners, self-promotion impossible, last-owner and billing-owner rules, IDOR: every group/member/invite route resolves membership first and answers `404` to non-members, member emails only for admins/owners, audit + mutation + outbox in one transaction, error codes consistent with the catalogue and api.md, migrations reversible and matching the model snapshot (snapshot test).
